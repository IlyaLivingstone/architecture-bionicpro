# Задание 3. Снижение нагрузки на базу данных

Что сделано по каждому пункту задания и где это лежит.

## Что нужно было сделать

1. Записывать сформированные отчёты в объектное хранилище с S3 API (MinIO).
2. При запросе сначала проверять наличие отчёта в хранилище: если он есть — отдавать
   ссылку на CDN, если нет — формировать, складывать в S3 и тоже отдавать ссылку.
   CDN — Nginx как reverse proxy с кешированием статических файлов.
3. Продумать обновление кеша CDN и структуру хранения отчётов.

## 1. Сервис отчётов и объектное хранилище

* `bionicpro-api/src/main/java/ru/bionicpro/api/storage/ReportStorage.java` —
  работа с MinIO: создание бакета, проверка наличия объекта, загрузка CSV,
  подписанная ссылка и удаление прошлых версий отчёта.
* `.../report/ReportService.java`: порядок работы при запросе отчёта:
  сначала ищется готовый файл в S3 (`findLatest`), и только если его нет —
  выполняется запрос к витрине ClickHouse, файл загружается в S3 и лишь затем
  выдаётся ссылка на CDN.
* `.../report/EtlStateCache.java`: сведения о периоде и версии витрины
  кешируются в памяти на минуту, поэтому повторные запросы уже сформированных
  отчётов не обращаются к OLAP-базе вообще.
* Ответ `GET /reports`: `{login, period, cached, etlVersion, url}`.
  Прямая выгрузка из витрины без хранилища и кеша осталась как `GET /reports/export`.

**Структура хранения:**

```
bionicpro-reports/<login>/<период>/usage-<версия витрины>.csv
пример: bionicpro-reports/user1/all_2026-10-05/usage-20261005T210342.csv
```

* `<login>`: отчёт лежит в «папке» пользователя, доступ к чужой папке получить нельзя;
* `<период>`: `all_<дата>` для полного отчёта или `<с>_<по>` при фильтре по датам;
* `<версия витрины>`: время последнего запуска ETL: пока витрина не обновилась,
  отчёт переиспользуется; после обновления ключ меняется.

**Обновление кеша.** Ключ объекта содержит версию витрины, поэтому после каждого
запуска ETL формируется новый объект, а прошлые версии удаляются из S3
(`deleteOlderVersions`). В CDN ключ кеша — это путь запроса, значит новый объект
кешируется отдельно и пользователь не получает устаревший отчёт. Записи старой
версии вытесняются по `proxy_cache_valid` (10 минут) и `inactive` (60 минут).

## 2. CDN на Nginx

* `nginx/conf.d/cdn.conf`: отдельная папка `nginx`, reverse proxy к MinIO
  с включённым кешированием (`proxy_cache_path`, `proxy_cache`, `proxy_cache_key`,
  `proxy_cache_use_stale`, `proxy_cache_lock`).
* Ключ кеша: только путь: подпись S3 приходит в query и на ключ не влияет,
  поэтому файл кешируется один раз, а ссылки могут быть разными.
* В ответ добавляются `X-Cache-Status` (MISS/HIT), `Cache-Control` и
  `Content-Disposition`, чтобы браузер скачивал отчёт файлом.
* Бакет закрыт: анонимный запрос к нему возвращает `403`. Сервис отдаёт
  подписанную ссылку, а Nginx проксирует запрос с заголовком `Host: minio:9000`,
  по которому проверяется подпись. Время жизни ссылки (час) больше времени жизни
  записи в кеше (10 минут).

## 3. Развёртывание

* `docker-compose.yaml`: сервис `minio` (конфигурация из репозитория спринта:
  `minio_user` / `minio_password`, порты 9000 и 9001), сервис `minio-init`
  (создаёт приватный бакет `bionicpro-reports`) и сервис `nginx-cdn` (порт 8082).
* ClickHouse переведён на порты `8123` и `9431`, чтобы не занимать порт MinIO.

## Как убедиться

```bash
docker compose up -d --build
docker compose exec airflow-scheduler airflow dags trigger bionicpro_reports_mart
```

Затем войти в веб-приложение (`user1` / `password123`) и нажать «Download Report»:
первый раз сервис ответит `cached: false` (отчёт собран и положен в S3),
повторный — `cached: true`; файл в обоих случаях скачивается по ссылке CDN.

Проверить содержимое хранилища и состояние кеша:

```bash
docker compose exec minio /opt/bitnami/minio-client/bin/mc ls --recursive local/bionicpro-reports
curl -sI "http://localhost:8082/reports/<логин>/<период>/usage-<версия>.csv?<подпись>" | grep -i x-cache-status
```
