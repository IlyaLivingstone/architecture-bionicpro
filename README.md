# BionicPRO — 9 спринт

Проектная работа курса «Архитектура ПО. Продвинутый уровень».
Веб-приложение показывает отчёты о работе протеза; аутентификация вынесена
в отдельный сервис, чтобы браузер не работал с токенами удостоверяющей службы.

## Что реализовано (Задание 1)

* **PKCE вместо Code Grant.** Клиент `reports-frontend` требует
  `code_challenge_method=S256`; обмен кода авторизации на токены выполняет
  сервис `bionicpro-auth` и присылает `code_verifier` только по back channel.
* **Токены не попадают в браузер.** Access- и refresh-токены хранятся в Redis
  в зашифрованном виде (AES-256-GCM) и привязаны к идентификатору сессии.
  Браузер получает только cookie `BIONICPRO_SESSION` с флагами `HttpOnly`
  и `Secure`.
* **Ротация сессии.** На каждом запросе к защищённому ресурсу сервис
  перепривязывает токены к новому `session id` и обновляет cookie — защита
  от session fixation.
* **Обновление токена на стороне сервера.** Время жизни `access_token` — 2 минуты,
  сессии — 30 минут; истёкший токен сервис обновляет по `refresh_token`.
* **LDAP представительства.** OpenLDAP подключён к Keycloak как федерация
  пользователей, группы LDAP маппятся на роли realm `user` / `prothetic_user`.
  Учётные записи представительства читаются из локального каталога, персональные
  и медицинские данные остаются в стране.
* **MFA.** Вход по одноразовому паролю обязателен для всех пользователей.
* **Яндекс ID.** Внешняя удостоверяющая служба подключена через Identity
  Brokering; профиль пользователя запрашивается у Яндекса и сохраняется
  в базе сервиса аутентификации.

Архитектура: `Task1/BionicPRO_C4_model_to-be.drawio` — поставляемая схема C4,
дополненная контуром управления учётными данными (PNG рядом).
Состояние realm после настройки: `keycloak/keycloak-results-export.json`.

## Что реализовано (Задание 2)

* **ETL на Airflow.** DAG `bionicpro_reports_mart` (`airflow/dags/reports_mart_dag.py`)
  по расписанию собирает телеметрию протезов и данные клиентов CRM и перезаписывает
  витрину за окно 30 дней.
* **Витрина в OLAP.** ClickHouse, таблица `reports.user_daily_usage` — одна строка
  на пользователя и день, ключ сортировки `(login, report_date)`;
  `reports.etl_state` хранит период, по который данные подготовлены.
* **Сервис отчётов.** `bionicpro-api` отдаёт `GET /reports` (CSV) и
  `GET /reports/availability`; отчёт читается из витрины одним SQL-запросом,
  вычислений в реальном времени нет.
* **Доступ только к своему отчёту.** Пользователь берётся из серверной сессии,
  параметры запроса на выбор пользователя не влияют; необработанный период
  возвращает `409` с подсказкой.
* **Кнопка в UI.** Веб-приложение скачивает отчёт по нажатию и показывает,
  по какую дату данные готовы.

Архитектура: `Task2/BionicPRO_C4_reports_to-be.drawio` (+ PNG).

## Что реализовано (Задание 3)

* **Отчёты в объектном хранилище.** Сформированный отчёт загружается в MinIO
  (`bionicpro-reports`) с ключом `<логин>/<период>/usage-<версия витрины>.csv`;
  повторный запрос берёт файл из S3, не обращаясь к OLAP-базе.
* **Раздача через CDN.** Nginx (`nginx/conf.d/cdn.conf`) проксирует запросы
  к MinIO и кеширует статические файлы; сервис отдаёт браузеру ссылку на CDN.
* **Закрытый бакет.** Анонимный доступ запрещён, ссылка подписывается сервисом;
  Nginx проверяет подпись у MinIO, а кеш отдаёт файл без повторных обращений.
* **Обновление кеша.** Версия витрины входит в ключ объекта: после запуска ETL
  формируется новый файл, прошлые версии удаляются из S3, а старые записи кеша
  вытесняются по TTL.

## Что реализовано (Задание 4)

* **CDC вместо выгрузок.** Debezium читает изменения таблицы `clients` через
  логическую репликацию PostgreSQL и отправляет их в Kafka (топик
  `bionicpro.public.clients`); массовые выгрузки из CRM больше не выполняются.
* **Приём в OLAP.** ClickHouse читает топик таблицей-движком `KafkaEngine`,
  а `MaterializedView` поддерживает состояние клиентов в `reports.crm_clients`.
* **Витрина на представлениях.** `reports.user_usage_mart` собирается
  материализованными представлениями при загрузке телеметрии и при изменении
  данных клиента, поэтому остаётся актуальной между запусками ETL.
* **Сервис отчётов на новой витрине.** API читает `reports.user_usage_mart`,
  а версия данных CRM входит в ключ отчёта в S3/CDN — изменение клиента
  автоматически инвалидирует готовый отчёт.

## Запуск

```bash
cp .env.example .env      # при необходимости укажите ключи Яндекс ID
docker compose up -d --build
```

После старта `keycloak-setup` досоздаёт в realm то, что нельзя описать
в файле импорта: LDAP-федерацию, маппинг ролей и обязательный OTP.
Витрина отчётности собирается DAG-ом `bionicpro_reports_mart` по расписанию;
запустить его вручную можно так:

```bash
docker compose exec airflow-scheduler airflow dags trigger bionicpro_reports_mart
```

Полная выгрузка realm:

```bash
sh keycloak/setup/export-realm.sh
```

## Учётные записи

| Пользователь | Пароль | Источник | Роль |
| --- | --- | --- | --- |
| `user1`, `user2` | `password123` | realm | `user` |
| `prothetic1`…`prothetic3` | `prothetic123` | realm | `prothetic_user` |
| `admin1` | `admin123` | realm | `administrator` |
| `john.doe`, `alex.johnson` | `password` | LDAP | `prothetic_user` |
| `jane.smith` | `password` | LDAP | `user` |

При первом входе Keycloak попросит настроить одноразовый пароль
(Google Authenticator или FreeOTP), при следующих — запросит код.

## Ключи Яндекс ID

Приложение регистрируется на <https://oauth.yandex.ru>. Полученные `ClientID`
и `Client secret` передаются переменными окружения `YANDEX_CLIENT_ID`
и `YANDEX_CLIENT_SECRET`, после чего применяются к Identity Provider `yandex`.
